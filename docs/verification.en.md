# Verification catalog

This catalog separates general theorems for arbitrary inputs from finite computational checks. A finite check applies only to its enumerated inputs; it is not a general correctness proof.

[日本語](verification.md) | [README](../README.en.md)

## Overview

| Area | General theorems | Proof status or boundary |
| --- | --- | --- |
| [CLI input](verification/stateful.en.md#cli-input) | Whitespace splitting agrees with the character-list specification; multi-value and single-value parsers agree with the `List.mapM` model | Standard-input IO layer |
| [Factorial](verification/arithmetic.en.md#factorial) | Implementation agrees with its recursive specification; monotonicity, bounds, and divisibility | General implementation correctness is proved |
| [Fibonacci](verification/arithmetic.en.md#fibonacci) | Fast doubling agrees with the recursive specification; recurrence, addition, and periodicity results | General implementation correctness is proved |
| [Prime factorization](verification/arithmetic.en.md#prime-factorization) | All-input implementation correctness against `FactorsCorrect`; specification-derived factor properties and uniqueness; product, factor bounds, divisibility, ascending order, and loop invariants | General proof complete; finite checks cover selected boundaries and large values |
| [Sorting](verification/sorting.en.md) | Arbitrary-input correctness and independent-checker acceptance for recursive and loop-based quick sort, merge sort, and heap sort; pure output strings from all sorting CLIs agree with independent MergeSort | General implementation correctness is proved; standard input/output IO is outside the scope |
| [Running median](verification/stateful.en.md#running-median) | Preservation under inserting any value into any invariant state; the `ofArray` invariant for arbitrary input lengths; success of the all-prefix checker; agreement of the median and its CLI-formatted output with the independent sorting specification; invariance under input permutations | General proof complete; finite checks cover only the domains listed below |

- [Arithmetic algorithms](verification/arithmetic.en.md): factorial, Fibonacci, and prime factorization
- [Sorting](verification/sorting.en.md): shared specification, quick sort, merge sort, and heap sort

Each detail page separates general theorems, finite checks, and execution boundaries outside the formal proofs.

HeapSort verification is split by responsibility: `HeapSort/HeapOperations.lean` contains the shared specification, heap model, and operation contracts; `HeapSort/Core.lean` contains heap construction, extraction, and general correctness; `HeapSort/FiniteChecks.lean` contains bounded checks. The existing import path `LeanExperiments.Verification.HeapSort.Spec` remains a compatibility entry point that imports all three modules. RunningMedian state-invariant definitions and foundational lemmas live in `RunningMedian/StateInvariant.lean`, while `RunningMedian/Spec.lean` remains the compatibility entry point.

## Proof scope and trust dependencies

Read verification results along two independent dimensions: the input domain and the proof's trust dependencies.

| Label | Input scope | Trust dependencies |
| --- | --- | --- |
| A | General theorem for arbitrary inputs | Only the accepted kernel axioms (`propext`, `Classical.choice`, and `Quot.sound`) |
| B | General theorem for arbitrary inputs | A's axioms plus helper axioms generated by `native_decide` |
| C | Finite domain explicitly identified by its name or definition | A bounded computational check; inspect the audit result separately for native-computation dependencies |
C identifies proof scope independently from trust dependencies. CI audits A/B general theorems and private helpers separately from C finite checks, and rejects `sorryAx` and unregistered dependencies. A B theorem still concerns arbitrary inputs, but it is not treated as closed under only the same kernel dependencies as A. The GitHub Actions summary reports, for general proofs and finite checks separately, how many actually depend on `native_decide` helper axioms. These counts are derived from the registered audit output on every run rather than maintained as fixed README values.

For new Lean consumers, import `LeanExperiments.Algorithms` for executable algorithms and `LeanExperiments.Verification` for specifications and proofs. The historical `LeanExperiments` umbrella remains for compatibility and imports both.

## Continuous build

GitHub Actions runs `lake build`, CLI checks, and negative regression tests for the audit tools. `verification_sources.json` registers every Lean source and namespace under Verification. CI checks the file set, import reachability from `LeanExperiments.Verification`, and the presence of built `.olean` files. Source theorems and lemmas are matched against explicit general and finite groups in the axiom manifest; scope is not inferred from theorem names. CI scans all Lean sources for `sorry`, `admit`, and ad hoc `axiom` or `constant` declarations, then audits kernel dependencies of public propositions, private helper theorems, bounded checks, and examples. For module-system files, where private names are hidden after import, CI recompiles the source to collect their dependencies. Ordinary general and private theorem groups may depend only on `propext`, `Classical.choice`, and `Quot.sound`. General theorems using `native_decide` for base cases or finite residue tables are registered separately, and generated helper axioms are restricted to registered targets. CI inventories public proposition declarations from Lean's elaborated Environment and compares them with the public manifest. Private proposition-valued `def` and `opaque` declarations, including generated helpers, are compared with a reviewed baseline.

A Lean Environment snapshot of 1,740 public declarations (including 1,497 propositions) records names, kinds, owning modules, pretty-printed types, and transitive axiom dependencies in `verification_api_baseline.json`. CI flags removals, additions, and changes to these fields for review. Type comparison uses Lean's pretty-printed strings: a difference triggers review but does not prove semantic inequivalence, and semantic equivalence is not automatically proved. Baseline changes are explicit and require review. The API snapshot and axiom audits record different evidence, and neither alone establishes that the specifications are appropriate. A successful build confirms that Lean accepts the definitions and proofs. Finite computational checks and CLI standard-input/output execution outside the formal proofs are separate evidence.

## Performance measurements

Run `python3 scripts/benchmark_algorithms.py --sizes 100 1000 5000 --repeats 3 --output benchmark.json` to measure recursive and loop-based heap, merge, and quick sorts plus the RunningMedian CLI on random, ascending, descending, and duplicate-heavy inputs. The JSON records end-to-end CLI time and GNU `time` child peak RSS, and each output is checked against a reference result. Measurements include parsing and formatting; they are not complexity proofs. Compare runs only with the Lean toolchain, OS, seed, and repeat count recorded and aligned.
